## 0. エグゼクティブサマリ

Stream Agent は「モデルの重みをリモートから必要分だけ取り出し、**ディスクのハード予算**を守りながら推論する」という明確な問題設定を持っている。設計（`Plan.md`）は非常に野心的で、キャッシュ会計・レンジ検証・マルチモデル配额・テレメトリの骨格は実際に動いている。一方で、監査前の状態は「**主張が実装より一歩先に進んでいる**」プロジェクトだった。

今回の監査で、以下を含む **P0 の correctness / 誠実性の問題** を修正した。

1. Hugging Face が Range を無視して `200 OK` を返した場合、旧実装はレスポンス本文を最後まで読んでから拒否していた（=静かな全量ダウンロード）。ストリームを閉じて本文を読まずに拒否するよう修正。
2. ローカルソースが 1 ブロック読むたびにファイル全体を読んでいた。`seek/read` の窓読みに修正。
3. `range_requests` が provider と runtime の両方で加算され、**すべての転送が 2 倍**に報告されていた。単一加算に修正。
4. `ttft_ms` が全バックエンドで「生成全体の時間」を指していた。first-token を観測できない場合は `null` にするよう修正。
5. GGUF の全量読みが metadata 会計を通り、**weight cache 予算を迂回**していた。weight shard は必ず weight cache を通すよう修正。
6. 共有ブロックのキャッシュヒット時に、読んだモデルの alias が `entry.refs` に追加されず、**マルチモデル配额が効かない**経路があった。修正。
7. selective MoE が未選択 expert をゼロ埋めしたまま路由され得る、危険な既定動作だった。**明示 opt-in + 失敗時 dense fallback + tensor identity 検査**に変更。
8. GGML の型テーブルが type 19 以降でずれており、量子化 GGUF のバイト範囲が**静かに誤っていた**。実ブロック表に修正し、未知型は fail loud に変更。

現時点のオフライン試験は **111 passed**（network 2 件は別枠）、カバレッジ **68%**。実モデル（4 MB の random-weight tiny Llama）での再測定は成功し、`range_requests=23` がログと完全に一致、`ttft_ms=null`、weight 4,131,280 B が 1 回だけ転送されることを確認した。

**結論**: 土台は本物。ただし現状は「研究用プロトタイプ」であり、世界水準のプロダクトではない。勝ち筋は **(A) ディスク予算付きマルチモデル推論ゲートウェイ**を楔にし、**(C) GGUF/MoE の省ストレージ実行**を旗艦デモにすること。フル機能の「エージェント」や「何でも動く推論サーバー」を追うと負ける。

## 2. 検証済みの事実（修正後の再測定）

環境: Windows 10、16 GiB RAM、RTX 3050 8 GiB、Python 3.11.15。
モデル: `hf-internal-testing/tiny-random-LlamaForCausalLM` @ `9fb191250dd56d0ba7ec9785a025ed29c03d5998`（4,131,280 B shard）。
条件: 8 MiB budget、4 generated tokens、262,144 B block、cold 1 run。

```text
downloaded_bytes_total     5,977,351
weight_downloaded_bytes    4,131,280   ← shard 全体を 1 回だけ
metadata_downloaded_bytes  1,846,071   ← tokenizer + config
range_requests             23          ← 18 (model) + 5 (metadata)
full_object_requests       0
cache hits / misses        74 / 16
ttft_ms                    null
generation_ms              194.26
tokens/s                   20.59
peak weight cache          4,393,424
```

`range_requests=23` の内訳はログと完全に一致する: 1 MiB header probe、64 B capability probe、256 KiB × 16 data block、metadata 5 ファイル。**2 倍計上は解消**している。

### この測定が証明すること

- 実在する Transformers モデルが、リモート Range とローカル cache だけで動く。
- 4 MB の shard を 8 MiB budget に収め、2 回目以降は cache から返せる。
- フルオブジェクト要求は 0。Range 非対応なら typed error で止まる。

### この測定が証明しないこと

- 品質のあるモデルが動くこと（random weight なので出力は無意味）。
- 27B / MoE / GGUF が動くこと。
- RAM/VRAM が bounded であること（bounded なのはディスクだけ）。
- TTFT が速いこと（測れていない）。
- prefetch が効くこと（未配線）。

## 3. 今回修正した P0 バグ（詳細）

### 3.1 HF の `200 OK` で本文を読み切っていた

旧 `_request_range` は `client.get()` の後に status を見て `response.content` に触れる経路があり、Range 非対応サーバーでは **モデル shard 全体をメモリに落としてから** `RANGE_UNSUPPORTED` を返していた。設計の「no silent full download」に反する。

修正: `client.send(..., stream=True)` で送り、`200` を受けた瞬間に `response.aclose()`。本文は読まない。`206` でも `Content-Range` 必須、返却 byte 数一致を検証。429 は再試行せず `Retry-After` を details に残す。テスト追加済み。

### 3.2 ローカルソースの全量読み

旧 `LocalDirectorySource.fetch_range()` は毎ブロック `target.read_bytes()` していた。4 GB ファイルを 8 MiB ずつ読むと O(n²) になる。

修正: `seek(start)` + `read(end-start+1)`。path traversal も `relative_to()` で拒否。テスト追加済み。

### 3.3 Range リクエストの 2 倍計上

`RemoteWeightProvider._fetch_block()` と `runtime._on_source_event("range_ok")` の両方が `range_requests += 1` していた。修正: provider 側を削除。metadata 取得も source がイベントを出すため、provider の手動加算も削除。

### 3.4 TTFT の捏造

`GenerationResult.ttft_ms` に `total_ms` を入れていた。これは「生成完了までの時間」であり TTFT ではない。修正: `float | None` にし、`model.generate` 一括呼び出しの backend は `None`。bench の表は `None` を `-` 表示。真の TTFT は token streaming 実装後に入れる。

### 3.5 GGUF 全量読みの会計迂回

`GgufBackend.load()` が `provider.read_file(gguf, 0, size-1)` を呼び、`read_file` は metadata store に書いていた。結果、90 MB の GGUF が `metadata_downloaded_bytes` に計上され、`cache_used_bytes=0` のまま「bounded cache」を名乗っていた。

修正: `read_file()` は `layout.shards` に含まれる path を必ず `_read_range()`（weight cache）に流す。GGUF は引き続き Level 1（全量取得）だが、少なくとも **weight 予算の内側**で動き、報告も正しくなる。tensor-level streaming は別作業。

### 3.6 共有ブロックの attribution 欠落

`CacheManager.fetch_block()` のヒット経路は `_touch()` するだけで `entry.refs` に読者を追加していなかった。モデル B がモデル A の block をヒットすると、B の `model_used_bytes` は 0 のまま。fixed quota が実質無効化される。

修正: ヒット時に `request.model_alias` を `refs` に追加して DB に persist。テスト追加済み。

### 3.7 Selective MoE の危険な既定動作

旧実装:

- `non_expert_names = [n for n in names if "experts" not in names]` の typo（`names` は list なので常に True）で expert も dense 取得していた。
- 未選択 expert をゼロで確保し、router が後から別 expert を選ぶと**ゼロ重みで計算**していた。
- `_post_hook` が param を `meta` に戻す一方、`_expert_full_tensors` は detached tensor を保持し、次パスでそれを再利用していた。

修正:

- `experimental_selective_moe=True` の明示 opt-in。`expert_specs` と `router_resolver` の両方を必須化。
- resolver 例外・空選択時は **dense に fallback**（部分ゼロで走らせない）。
- full tensor の再利用前に「module に実際に install されているか」を identity で検査。
- `_post_hook` で `_expert_full_tensors` を clear。
- provider の `read_expert` が「1 行」ではなく宣言された packing に基づく正しい shape を返すよう修正。

### 3.8 GGML 型テーブルのずれ

旧表は type 19 以降がずれ、`I8` を 136 B/block、`BF16` を 74 B/block としていた。量子化 GGUF の byte range が静かに誤る。

修正: `GGML_TYPES = {id: (name, bytes_per_block, elements_per_block)}` を実装し、Q4_0=18/32、Q8_0=34/32、Q4_K=144/256、BF16=2/1、F64=8/1、MXFP4=17/32 などを正しく設定。未知 type と block 非整除は `ModelFormatUnsupported`。テスト追加済み。

### 3.9 その他の修正

- `validate_config` が `storage.quota_policy == "fixed"` のときしか fixed 個別配额を合算していなかった。既定 policy が elastic でも、明示 fixed の合計は検証するよう修正。
- `bench.clear_cache()` が `_evicted_content_hashes` を残し、cold run が「再取得」と誤判定され得た。clear + reset に修正。cold reset 自体の eviction も計上しない。
- server が `stream` を常に field として広告していた。backend capability を見て動的に広告。fixture の `supports_streaming` を False に修正（実際は一括生成）。
- server が `stop` を受け取るのに無視していた。`ModelSession.generate()` で stop 文字列を適用し、`finish_reason="stop"` に。計算は削減できないため「テキストだけ truncate」と明記。
- `read_slice()` / `read_expert()` が full tensor の shape を返していた。slice shape を返すよう修正。

## 4. まだ残る重大な課題（P1）

### P1-1. 実推論の検証が弱すぎる

`transformers_backend` の coverage は 13%。実質「tiny random model が 1 回動いた」だけ。lazy/eager の差、tied weights、quantized dtype、device 転送、OOM、長い prompt、batch、seed 再現性が未検証。

**次**: `SmolLM2-135M-Instruct` など小さくても品質のあるモデルで、
(a) 同一 prompt の出力が全量ローカル実行と一致、(b) lazy/eager で一致、(c) 3 seed で再現、を CI に入れる。random model の perplexity 比較では不十分。

### P1-2. lazy mode の bytes/token が現実的でない

lazy は 1 token ごとに全 layer を再取得する。8 MiB budget でも 4 token で 5.9 MB 転送、32 token なら 10 MB 超。これは「小さい cache のコストを見える化」としては正しいが、プロダクトとしては遅すぎる。

**次**: layer 単位の LRU 常駐（budget 内で「直近 N layer」を保持）、eager とのハイブリッド、prefetch の配線。目標は「8 GiB budget で 7B モデルを 10 tok/s」など、現実的な線。

### P1-3. RAM/VRAM が bounded でない

eager は全パラメータを実デバイスに展開する。lazy も 1 layer 分は必要。`min_working_memory_bytes=0` は「保証しない」の意味だが、README の「storage-budgeted」と混同されやすい。

**次**: `peak_rss_bytes`, `peak_vram_bytes` を実測して report に入れる。`--max-working-memory` を追加し、超えたら typed error。少なくとも「ディスク予算 ≠ メモリ予算」を UI で明示。

### P1-4. GGUF が Level 1 のまま

全量取得は「bounded cache」の意味を弱める。90 MB の GGUF を 8 MiB cache で開くと、cache は刻々と evict しながら results に全量を保持する。動くが、主張と実装が微妙にずれる。

**次**: `GgufBackend` を tensor range で読む Level 2 へ。Transformers の `gguf_file=` はローカルファイル前提なので、`gguf` パーサで tensor を個別に materialize する独自ローダ、または llama.cpp の mmap を差し替えるアダプタが必要。まずは `llama-cpp-python` の `Llama` に `tensor_split` ではなく「range-backed file-like」を渡せるか検証。あわせて、現在 header を最大 8 MiB しか読まないため、巨大な metadata を持つ GGUF では parse が truncation で失敗する。段階的に読み足す実装が必要。

### P1-5. selective MoE はまだ「実験」以上ではない

unit test は materialiser の byte 削減を見るが、モデル出力の正しさは見ていない。Qwen3-MoE の `gate_up_proj` 形状・router の top-k・shared expert・aux loss の扱いを E2E で確認する必要がある。

**次**: `tiny-random/qwen3.5-moe` で (a) dense と selective の logits 一致（許容誤差）、(b) 選択 expert が毎 token 完全に取得されること、(c) resolver 失敗時に dense fallback すること、を test 化。

### P1-6. prefetch が未配線

`PrefetchScheduler` は session に生成されるが `schedule()` が呼ばれない。`max_bytes` も `_inflight_bytes` を更新しないため実効がない。README の「implemented (bounded)」は過大。

**次**: 次 layer の tensor 名を backend が宣言できる interface を追加し、`_pre_hook` から `schedule()`。ただし prefetch が current layer を evict しないよう、reservation に priority を付ける。難しければ README から「implemented」を外す。

### P1-7. server の実装範囲

- `stream=true` は全 backend で 400。OpenAI クライアントの多くは stream を試すため、最初の体験が悪い。
- `stop` はテキスト truncate のみ。
- 認証・rate limit・max body 以外の防御がない（loopback 前提だが、`allow_remote_bind` を true にすると危険）。
- `/metrics` は Prometheus 形式でなく JSON。

**次**: 真の token streaming（backend に `stream()` を追加）、SSE、`stop` の生成時適用、optional bearer token、Prometheus exporter。

### P1-8. 測定器にテストがない

`bench.py` は coverage 0%。「測定の正しさ」を売りにするプロジェクトで、測定器が未テストなのは致命傷。

**次**: 固定 fixture で「cold 1 run の bytes/token が期待値」「warm run で weight_downloaded_bytes=0」「budget を超えない」「ttft は None」を test 化。

### P1-9. セキュリティ・法務

- HF token は env のみ。credential store は未実装。
- モデル license の review は「pending なら block」だが、license id の解釈は人手。
- `allow_remote_code` は false 既定だが、`trust_remote_code=False` を渡しているだけ。将来 `true` にする経路の監査が必要。
- ローカル server は loopback でも、同一マシンの他プロセスからは叩ける。API key があるとよい。

### P1-10. ドキュメントの残存過大主張

今回 README/EVIDENCE を修正したが、以下は引き続き注意:

- 「C2 Xet/CDN range path」→ 実装は HTTP Range であり、Xet 固有プロトコルではない。README は修正済み。
- 「C6 implemented」→ library only に修正済み。
- 「GGUF inference なし」→ 実は Level 1 はある。README は修正済み。
- ベンチの `cache_hit_ratio` は block 単位。byte 単位の `useful_reuse_ratio` と併記する。

## 5. 製品としての位置づけ（3 案）

### 案 A: ディスク予算付きマルチモデル推論ゲートウェイ（推奨）

「複数のモデルを、明示したディスク予算と監査可能な通信量で、ローカル/エッジで動かす」。
- 顧客: ノート PC・工場端末・店舗サーバー・個人開発者。
- 価値: 「モデルを消さないと入らない」を「予算内で必要な分だけ持つ」に変える。
- 競合: Ollama（全量前提）、llama.cpp（全量前提）、PULSAR/Edge0（研究色が強い）。
- 勝ち筋: **グローバル硬予算 + マルチモデル配额 + 正直なテレメトリ + OpenAI 互換 endpoint**。
- リスク: 「小さいモデルなら全量持てばいい」という現実。7B 量子化で 4 GB なので、8 GB 予算なら全量入る。**30B MoE 級**でないと価値が伝わりにくい。

### 案 B: サーバーレス/マルチテナント向け「リモート重みキャッシュ層」

モデル実行そのものではなく、Lambda/Cloud Run/K8s の**共有 weight cache** を提供する。
- 顧客: 推論 SaaS、CI、マルチテナント GPU 基盤。
- 価値: cold start の weight download を削減、テナントごとの disk quota を強制。
- 競合: HF Hub の CDN、Xet、S3 Express、Modal/RunPod の snapshot。
- 勝ち筋: **テナント分離 + 監査 + 範囲検証**。ただしクラウド事業者に飲み込まれやすい。

### 案 C: GGUF + MoE 特化「省ストレージ大規模 MoE 実行」

30B-A3B 級の MoE を、8 GB VRAM / 16 GB RAM / 小さな disk cache で動かす。
- 顧客: 個人・小規模チーム・オンプレ。
- 価値: 「30B 級を laptop で」はデモ価値が非常に高い。
- 競合: llama.cpp の `--n-cpu-moe`、KTransformers、PowerInfer。
- 勝ち筋: **expert-level range streaming + router-aware prefetch + 正確な bytes/token**。ただし llama.cpp がすでに強い。

**推奨**: A をプロダクトの入口にし、C を旗艦デモにし、B を収益化の選択肢にする。A の「予算と監査」は地味だが、C のデモがないと誰も振り向かない。C のデモがないまま A を売ると「Ollama でいい」で終わる。

## 6. 世界水準にするための条件

1. **再現可能なベンチマーク**: 固定ハード・固定 revision・固定 prompt・固定 budget で、誰でも同じ数字を出せる。`scripts/` と `docs/benchmarks/` を CI で回す。
2. **正しさの証明**: random model ではなく、実モデルの logits/生成一致。dense vs lazy vs selective の一致。
3. **予算の強制**: disk だけでなく RAM/VRAM も。超えたら落ちる。silent に超えない。
4. **観測性**: bytes/token、TTFT、tok/s、peak disk/RAM/VRAM、eviction、refetch、hit ratio（block/byte 両方）。
5. **API 互換**: OpenAI chat completions + streaming + stop + usage。MCP。SDK（Python/TS）。
6. **安全性**: token を漏らさない、remote code を実行しない、license review、loopback 既定、optional auth。
7. **ドキュメント**: 「できること」と「できないこと」を同じ強さで書く。今回の監査でその基盤を作った。
8. **コミュニティ**: ベンチ結果の投稿テンプレ、再現スクリプト、good first issue、RFC。

## 9. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| HF の rate limit / ToS | デモが止まる | backoff、`Retry-After`、キャッシュ、公式ミラー、Xet |
| モデル license | 配布・商用不可 | license review、README 明記、ユーザー責任 |
| 「Ollama で十分」 | 価値が伝わらない | 30B MoE デモ、予算遵守、監査ログ |
| llama.cpp の追い上げ | 差別化消失 | マルチモデル予算・サーバー化・観測性に寄せる |
| 小さい cache の遅さ | 体験が悪い | layer 常駐、prefetch、eager 併用、UI で trade-off 表示 |
| セキュリティ | local server の悪用 | loopback 既定、auth、remote code 禁止 |
| 測定の信頼 | 数値が疑われる | 測定器の test、生ログ公開、再現 script |
